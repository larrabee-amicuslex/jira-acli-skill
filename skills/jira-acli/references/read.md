# 읽기 절차 — 내용·코멘트·첨부 확인하기

읽기는 **아무것도 바꾸지 않는** 동작이므로 확인 게이트가 필요 없습니다. 대신 두 가지를 지킵니다.

- **원본 JSON을 사용자에게 붙여넣지 않습니다.** 항상 한국어 문장이나 짧은 목록으로 다시 씁니다.
- **없는 걸 있다고 하지 않습니다.** 특히 첨부 파일 내려받기는 불가능합니다(4번 참고).

시작 전 `SKILL.md` 0.5의 진입 점검이 통과돼 있어야 합니다. 통과했다면 그걸로 끝이고, 통과하지
못했을 때만 `references/entry-check.md` 를 엽니다.

---

## 1. 작업 항목 본문 읽기

```bash
acli jira workitem view <KEY> --json
```

- **키는 플래그 없이 그대로** 붙습니다(`view` 만의 예외). 예: `acli jira workitem view PROJ-123 --json`
- 기본으로 돌아오는 필드는 키·유형·제목·상태·담당자·설명입니다.
- **기본 응답에 담기지 않은 필드는 `null` 로 옵니다. `null` 은 "값이 없다"가 아니라 "이 응답에
  담기지 않았다"는 뜻입니다.** 실제로 라벨이 붙어 있는 항목도 기본 `view --json` 응답에서는
  `labels` 가 `null` 로 나오는 것이 관측됐습니다. 그 값을 보고 "라벨 없음"이라고 말하면 **거짓말이
  됩니다.** 확인해야 하는 필드는 반드시 이름을 지정해 다시 조회하고, 그 결과로 판단합니다.

  ```bash
  acli jira workitem view <KEY> --fields "labels" --json
  ```

  같은 이유로 코멘트도 기본 응답에 없습니다(`--fields "comment"`). 값이 안 보이면 "없다"가 아니라
  **"확인해 보겠습니다"** 라고 말하고 필드를 지정해 다시 읽습니다.
- 설명(description)은 서식이 들어간 구조(ADF)로 올 수 있습니다. 그 구조를 그대로 보여주지 말고
  **읽어서 요약/평문으로 다시 씁니다.**
- 사람이 눈으로 보기만 하면 되는 경우에는 `--json` 없이 실행해도 됩니다. 다만 출력 형태는 환경과
  필드에 따라 달라질 수 있으니, 읽기 어려우면 `--json` 으로 받아서 직접 정리해 보여주세요.

사용자에게 보여줄 형태(예):

```text
PROJ-123 · 작업(Task) · 상태: <조회된 상태> · 담당: <조회된 담당자>
제목: <제목>
내용 요약:
- <요점 1>
- <요점 2>
```

## 2. 코멘트 읽기

```bash
acli jira workitem comment list --key <KEY> --json --paginate
```

- 여기서는 키가 `--key` 입니다(1번과 다름).
- `--paginate` 를 쓰면 모든 쪽을 다 가져옵니다. 도움말상 이때 `--limit` 은 무시됩니다.
- 최근 것만 보면 될 때는 `--limit 10` 으로 줄여도 됩니다.
- 코멘트가 많으면 전부 나열하지 말고 "총 N개, 최근 3개 요약" 형태로 줄여서 보여주고, 더 필요하면
  말해달라고 합니다.

## 3. 검색해서 찾기

키를 모르고 "그 이슈"라고만 할 때 씁니다.

```bash
acli jira workitem search --jql "project = <your-project> ORDER BY updated DESC" --fields "key,status,summary" --limit 20 --json
```

- 프로젝트 키를 모르면 먼저 `references/config.md` 의 프로젝트 조회를 씁니다.
- 위 형태(프로젝트 지정 + 정렬)는 동작이 확인된 기본형입니다. 검색어로 좁히고 싶으면 Jira 검색식(JQL)에
  조건을 덧붙일 수 있지만, JQL은 Jira 쪽 문법이라 조건에 따라 거부될 수 있습니다. 거부되면 **기본형으로
  되돌아가서** 결과를 받아 온 뒤, 우리가 직접 제목을 훑어 후보를 골라 보여줍니다.
- 항목이 많아 기본 개수로 부족하면 `--limit` 을 늘리거나 `--paginate` 로 전부 가져옵니다.
- 후보가 여러 개면 목록으로 보여주고 사용자가 고르게 합니다. **임의로 하나를 고르지 않습니다.**
- 검색식(`--jql`)은 **읽기에서만** 씁니다. 바꾸는 명령에는 절대 붙이지 않습니다.

## 4. 첨부 파일

두 가지 조회 방법이 있고, 목적이 다릅니다.

```bash
acli jira workitem attachment list --key <KEY> --json
```
→ 간단한 목록입니다. 확인된 응답은 첨부마다 id / 파일명 / 크기만 담고 있습니다.
"첨부가 있는지, 몇 개인지, 얼마나 큰지"를 볼 때 씁니다.

```bash
acli jira workitem view <KEY> --fields "attachment" --json
```
→ 상세 정보입니다. 확인된 응답은 첨부마다 파일명·크기·형식(mimeType)·등록 시각·등록자와 함께
`content` 주소를 담고 있습니다.

### 첨부에 대해 지켜야 할 것

- **내려받기·올리기 명령은 존재하지 않습니다.** "받아서 열어볼게요", "올려드릴게요" 라고 절대
  말하지 않습니다. 이 스킬이 할 수 있는 것은 **목록과 정보를 알려주는 것까지**입니다.
- 파일 내용을 봐야 하면 브라우저로 안내합니다:

  ```bash
  acli jira workitem view <KEY> --web
  ```

  또는 사용자가 평소 쓰는 Jira 화면에서 해당 항목을 열도록 안내합니다.
- 응답에 들어 있는 `content` 주소를 사용자에게 그대로 주지 않습니다. 확인된 사례에서 그 주소는
  사용자의 Jira 사이트 주소가 아니라 Atlassian이 운영하는 API 호스트를 가리켰습니다. 브라우저에
  붙여넣어도 기대한 대로 열린다는 보장이 없고, 비전문가에게는 혼란만 줍니다.
- 첨부가 하나도 없으면 "첨부 없음"이라고 분명히 말합니다(빈 목록을 침묵으로 넘기지 않습니다).

사용자에게 보여줄 형태(예):

```text
첨부 3개 (총 약 1.2MB)
1. <파일명> — 이미지, 약 400KB, <등록 시각>
2. ...
파일 내용은 브라우저에서 열어 확인하세요: acli jira workitem view PROJ-123 --web
```

## 5. 출력 렌더링 규칙

- JSON, 표 형식 원본, 필드 이름(`customfield_10021` 같은 것)을 그대로 노출하지 않습니다.
- 상태·유형·담당자는 **조회된 값 그대로** 씁니다. 번역하거나 비슷한 말로 바꾸지 않습니다.
  (상태 이름은 나중에 상태 변경에서 그대로 다시 써야 하는 값입니다.)
- 길면 줄입니다. 사용자가 원하면 더 보여주겠다고 덧붙입니다.
